# Foreground OCR service

`gptgrep ocr serve --config CONTROL_JSON --token-env GPTGREP_OCR_SERVE_TOKEN` is an explicit, native CLI foreground service. It binds loopback, defaults to `127.0.0.1:8828`, and stops accepting work on phase expiry, SIGINT or SIGTERM before awaiting owned child stop, reap and pipe drain. Ordinary search and ask never start OCR. The Node wrapper remains a bounded one-shot interface and rejects this long-running command.

This implementation is source-qualified independently of actual listener, native image, confidence-mode and backend qualification. Operator profile references do not prove an observed served model, effective effort/tier, semantic accuracy, OS isolation or process RSS. The requested native profile is exactly `gpt-6-luna`, `max`, `fast`, with no fallback. No native account alias or machine-specific path is built into the service.

Supply a bearer token of 32–256 visible ASCII bytes through the selected environment variable. Browser Origin requests and CORS preflights are rejected. The token is checked before body parsing, retained only as a digest, and omitted from errors, startup output, Debug values, OCR prompts and configuration frames. The selected variable and default service-token variable are removed from each service-owned Codex child command. Other caller-owned native account environment follows the existing OCR host policy. No global environment mutation occurs. Development checks use synthetic values and do not inspect credentials.

## Explicit control snapshots

The command reads one operator-selected regular JSON file, at most 16 KiB, with schema `gptgrep.ocr.serve.v1`. Unknown and duplicate fields are rejected. `--expected-control-sha256 SHA` optionally requires its exact bytes. Relative paths resolve against that control file’s directory. These explicitly selected control and source-input reads are distinct from native authentication/configuration discovery; their ownership and authorization remain the caller’s responsibility.

| Field | Meaning |
| --- | --- |
| `bind` | Optional loopback address, default `127.0.0.1:8828`; non-loopback addresses and port zero fail. |
| `source_root`, `prepared_root` | Existing source-only and prepared artifact roots for full-task custody. |
| `spool_root`, `claim_root`, `raw_results_dir` | Existing private 0700 directories for compatibility uploads, request claims and actual raw model results. All three are distinct and outside source, prepared and native-home namespaces. |
| `codex_home`, `codex_bin` | Explicit existing caller-owned native account home and standard pinned binary (`codex` by default). No login, account substitution or credential copying. |
| `runtime_profile` | Explicit `OcrRuntimeProfile` JSON, at most 16 KiB; exact binary/source/schema/descriptor/policy binding. |
| `task_catalog` | Optional `gptgrep.ocr.task-catalog.v1`, at most 8 MiB, containing `tasks: [{source_relative_path, task}]`; enables full-task route only with the existing exact-mode accepted image qualification reference. |
| `compatibility_profile` | Optional separately versioned `CompatibilityRuntimeProfile` JSON, at most 16 KiB; enables `/ocr` only with fresh confidence-mode qualification. At least one route must be configured. |
| `phase` | Explicit `gptgrep.ocr.service-phase.v1`, at most 16 KiB. |
| `resources`, `max_connections` | Optional tighter parser `ResourceBudget` and 1–8 connection cap (default 8). Resource counters are shared across tasks and retained writes. |

The phase contains `run_id`, `plan_sha256`, the complete `original_clock_anchor`, `ledger_path`, and `limits: {max_admissions, max_concurrency, ledger_bytes}`. The anchor comes from a separately owned original phase; serve never captures or renews it. Limits admit 1–1024 total charged attempts, 1–2 native slots, and a bounded 8 KiB–1 MiB journal large enough for the finite inventory. The historical 24-page pilot and legacy v1 journal remain unchanged; this product phase is independently versioned.

By default both the journal and stable lock must exist. `--initialize-ledger` permits a create-only attachment of the supplied namespace; an existing pair must match its full original anchor, run, plan and limits. Partial, missing joined, mismatched or changed state fails rather than resetting or refunding reservations. Unknown submissions remain charged and quarantined. The request journal independently records unknown before native admission; repeating that request cannot resubmit it. Completed exact task/profile/source-bound results may be reused only after revalidation.

## Routes and lineage

Authenticated `POST /v1/ocr/tasks` accepts `{"schema_version":"gptgrep.ocr.service.request.v1","task": OcrTask}` in at most 128 KiB. The server compares the entire serialized task with its held catalog. Skipped local paths are restored solely from the server-owned source relative path and artifact IDs/relative paths, then read through held directory/file custody. Caller wire paths have no authority. Successful full results retain source, prepared, image, profile, request, actual response and delivery bindings. The service does not publish a generation; normal core validation remains required.

Authenticated `POST /ocr` is separately qualified LiteParse compatibility. It accepts the pinned PNG multipart contract: `file` named `image.png` with `image/png`, optional bounded `language` (default `eng`), one image no larger than 1 MiB and 16 KiB multipart overhead. It returns `{"results":[{"text":"...","bbox":[0,0,width,height],"confidence":NUMBER}]}`. Text is raw transcription of the complete submitted image; the box is the submitted image extent, not detected word geometry. Confidence is the actual model-reported uncalibrated value in `[0,1]`, never fabricated, threshold-raised or inferred from unavailable data. Missing/null/nonfinite confidence, partial/unreadable status or changed bindings fails. This image-only result has weaker lineage, no original-document OCR coverage or generation publication authority, and no polygons or word boxes. JPEG compatibility is currently unsupported.

Confidence output has its own versioned task/result schema, prompt, mode/language policy hash and runtime qualification reference. Legacy full-task region serde bytes, digests, instructions, accepted receipts and private pilot remain compatible. An old full-task receipt cannot authorize the confidence mode. The explicit `OcrHostExecutor::probe_compatibility` qualification frontdoor uses the same finite pool and owned cleanup with an unqualified mode profile; it does not promote that profile or publish anything. Its runtime use requires separate caller authority.

## Bounds and observations

One service-owned aggregate logical working budget admits catalog JSON from regular-file metadata before its buffer is allocated, retains catalog/phase-journal/claim/header shares, and reserves a request-body share before collection and parsing. Once validated task or image dimensions are known, it reserves the complete job envelope before image decoding and native allocations. Shared clones retain the same counter. Incoming native RPC trees take an additional counted share before buffering/parsing; their trusted fields are moved out and the tree is released before image decode. A service-only usage object exceeding 4 KiB is refused before cloning, without fabricating missing usage. Response bytes carry their share through all queued `Bytes` clones/slices, so returning from the job does not release retained HTTP data. Two ordinary small-image jobs fit the default 256 MiB allowance; larger images, simultaneous large native frames, large retained catalogs or tighter totals can refuse capacity before the next owned allocation. These are conservative logical buffer allowances, separate from the unchanged staging counter and physical/native RSS. Native work uses at most two concurrent slots, one turn per task, eight mediated calls and the smaller of 180 seconds and the original phase deadline. HTTP has at most eight live connections, no keepalive, 32 headers, a 16 KiB header buffer, 10-second header and 15-second body bounds. Full responses and sanitized errors fit a 256 KiB response envelope. Parser limits may be tighter and refuse valid large inputs; resource caps do not claim whole-process/native RSS or OS-enforced disk reservation.

Startup emits bounded `gptgrep.ocr.serve.lifecycle.v1` with status `prepared` and `listener_ready:false`; it is not proof of a successful bind. Errors always use bounded JSON stage codes and omit token values, private paths and arbitrary native diagnostics. Every claimed fresh or cached request is registered as one permit-owning worker before its first asynchronous custody check. Interrupted HTTP requests request cooperative cancellation; blocking custody/hash/image work retains capacity, and shutdown awaits that same owner and any native cleanup. Local stop/reap/drain is awaited, while an unknown remote completion remains unknown and quarantined. Blocking source/hash operations are bounded and awaited on workers; hard preemption and remote cancellation are unqualified.

Offline tests cover in-memory HTTP/protocol behavior, strict phase state, confidence and custody bindings, token inheritance removal, and CLI pre-effect failures. They launch no listener, native Codex, provider call or actual phase. Actual loopback availability, native model/image influence, fresh confidence calibration/semantics and operating-system guarantees require distinct runtime qualification.

The optional control field `codex_state_dir` selects an existing canonical directory
with an existing `logs` child. The runtime uses it for `sqlite_home` and `log_dir`;
`codex_home` still selects authentication and profiles. Missing or symlinked state
paths fail before native admission. Omission preserves the original home binding.
Rich ingestion exposes the same setting as `--ocr-codex-state-dir`.
