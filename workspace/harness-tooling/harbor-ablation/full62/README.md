## GPTgrep full62 → Harbor Adapter

Portable adapter for the private paired SEARCH comparison. This package contains the adapter, agent, reader, verifier, aggregation source, a uv lockfile and synthetic regressions. It includes no private tasks, corpus, credentials or experimental results. Synthetic tests run against the installed Harbor 0.24.0 interfaces; the actual 124-trial comparison remains unrun.

For a fresh checkout, [development setup](../../../../docs/development.md) covers
Rust/PDFium, independent device login, the standalone INDEX helper, Decisions
credentials and the uv environment. [Experimental status](../../../../docs/experimental-status.md)
separates implemented source from current live outcomes. The official native
SEARCH reader in the common base and the guarded standalone INDEX helper are
different roles; the two SEARCH arms must still share their exact selected reader.

## Overview

The complete frozen historical development cohort supplies 62 tasks over 34 documents at runtime. Each task produces a GPTgrep arm and a raw-document native Codex arm: 124 Harbor trials, 62 paired outcomes. No task is selected by its content, answer, filename pattern or evidence location. This is a compatibility comparison and is not an unseen holdout.

Both SEARCH arms bind one native Codex reader binary and request `gpt-6-luna`, `max`, `fast`. The native metadata convention normalizes requested `fast` and reported `priority` to `priority`; neither proves the actually served profile. GPTgrep-specific tools are the intended treatment difference. The runtime records both exact permitted tool sets, shared generic raw-document capabilities, sandbox/account/budget rules and observed qualification mismatches. INDEX may use a different independently admitted helper; its identity is not required to equal the SEARCH reader binary.

The primary outcome is frozen question/reference answer equivalence. Every task stays in its arm's denominator of 62. Operational failures and missing outputs are zero; valid answers with unavailable judging are unknown, with bounds. Prebuilt INDEX work and judging remain outside primary SEARCH reward and cost. Their ledgers remain necessary for whole-experiment accounting.

## What is GPTgrep full62?

This is the repository's same-Codex SEARCH comparison defined in `SPEC.md` and its runtime-selected frozen cohort. It compares actual configurations, not a claim of isolated search-algorithm causality. Raw Codex receives raw documents only and may perform ordinary extraction/rendering during its query deadline; GPTgrep receives the same raw documents plus its prebuilt raw-only index. The private cohort's source/license/custody remains with the project owner. No dataset publication or redistribution is performed here.

## Adapter Features

- Real Harbor `BaseAgent.setup/run` integration, using the installed 0.24.0 API.
- Stock Docker environments and a separate verifier built from `tests/Dockerfile`; no custom environment implementation is needed.
- Runtime-loaded finite document/index lists and strict file digests. No discovery or downloads.
- Concrete GPTgrep `ask` and bare `codex exec --json` entrypoints. Image/account/schema qualification is required before any run.
- A bounded answer envelope crosses into the primary verifier. Native operational records remain in `/logs/agent/operational.json`, outside transferred artifacts. Gold/reference data exists only in the separate verifier build context.
- Complete-answer judging; no truncation to fit a judge. The Judge requests native structured output with the frozen response schema. Unavailable, non-JSON or schema-invalid judging retains unknown.
- Fixed-denominator paired cells, unknown bounds, document-cluster bootstrap, McNemar diagnostic, failure-aware time, usage/cost unknowns and optional separately produced grounding sidecars.
- The complete synthetic 124-task conversion is checked with Harbor's real `JobConfig`, `TaskConfig`, verifier resolver and `BaseAgent`. Docker, native permission effectiveness and model behavior require the selected runtime qualification.

The owner must select an authorized context created through the product's existing execution front door in the target Linux namespace. Both budget and ledger paths are denied to model tools. Three limits follow from that shared ledger:

- **200-submission cap for the whole cohort.** `max_submissions` is at most 200 per ledger, and every reservation is permanent, including failed and unknown outcomes. All 62 treatment trials draw on that one allowance, and a joined Ask stops when it is exhausted.
- **24-hour deadline window.** `decisions-budget init` fixes the deadline at most 86,400 seconds after creation, and nothing renews it. That one window must cover materialization, the 248 role-image builds and all 124 sequential trials, including every trial's reader and Judge deadlines.
- **A VM restart invalidates the ledger.** The run clock is bound to the boot identity and time namespace of the Linux kernel that created it, which is the Docker VM's kernel for containers. After that VM restarts, every join fails closed; a new ledger and a new run are required.

Its exact fields are `schema="gptgrep.harbor.decisions-preparation.v1"`, a `{path,bytes,sha256}` `seed` pin, `controls_directory`, `financial_family_directory`, `trial_state_directory`, `max_concurrent_batches=1`, and `sole_writer=true`. Its `gptgrep.current_decisions.preparation_seed.v1` contract binds the unchanged financial budget and digest, the financial family at `/opt/full62-private/financial-family`, authority/review/source file pins under `/opt/full62-private/controls`, `max_sdk_submissions` in 1–200, `cumulative_call_limit=2000`, and the selected sole-writer condition. These pins reference actual owner authorization and independent review; the adapter cannot create approval.

This mode requires the independently qualified private product bundle that implements `--harbor-prepare-input` and `--harbor-prepare-input-sha256`. The treatment mounts the complete existing financial family read/write, the selected controls read-only, one unique empty trial directory read/write, and a shared cohort writer-lock file. Neither Raw nor Judge receives those mounts. Materialization creates 62 distinct trial directories and one exclusive writer-lock file; a consumed state root cannot be materialized again. The nonblocking writer lock spans preparation and the actual Ask process. It prevents overlap among readers using this cohort's lock; the owner must separately exclude every other writer to the same financial family.

After the original reader deadline starts, the private preparer receives the same Ask options, question digest, runtime binding digest and absolute deadline, without provider credentials. It creates one SDK context in the current Linux namespace, preflights genuine source-generated request groups, and exports an existing-ledger budget plus an immutable attachment plan into `/opt/full62-private/trial`. It never submits a provider request or resets the financial family. Input and preparation claims use create-new files, so failure does not authorize another attempt. The actual Ask joins that original context and uses `--max-concurrent-batches 1`; preparation and execution share the original outer deadline. The public wrapper verifies the returned file pins and joins before adding only `GPTGREP_DECISIONS_ATTACH_PLAN` and `GPTGREP_DECISIONS_ATTACH_PLAN_SHA256` to its sanitized product environment. The native wrapper strips both variables and the provider key. The private financial observer settles the complete validated response before usage projection and fails a final unknown-cost or model-drift response while retaining its liability and receipt. The per-trial SDK ceiling and cumulative 2000-call ceiling remain separate controls. No corpus or candidate limit is changed by this integration.

For a `legacy_text` cohort without any shared ledger, select `decisions_mode="invocation_bounded"`. The treatment Ask receives no `--decisions-budget` and no ledger, budget, control or lock mount. Each Ask uses the product's own single-invocation context, which admits at most 200 Decisions submissions (`MAX_SUBMISSIONS` in `gptgrep-jev`); no allowance carries between trials. This mode requires two runtime fields. `decisions_cost_cap_usd` is the owner-approved USD cap for the whole cohort. `decisions_prompt_price` is `{model, usd_per_million_prompt_tokens, provenance}`: `model` must equal `jev_model`, and `provenance` is a strict `{path,bytes,sha256}` host pin of the owner's price evidence, verified at validation and never copied into a task. The worst case of one submission prices every byte of the product's 64 KiB request bound (`MAX_REQUEST_BYTES`) as one prompt token at the pinned rate. Validation requires 62 treatment trials × 200 submissions × that worst case ≤ `decisions_cost_cap_usd`, in exact decimal arithmetic over the JSON numbers; otherwise `decisions_cost_cap_preflight` stops before any task exists. The preflight output records every term of the bound. The bound covers prompt tokens only; completion tokens and provider-side additions are outside it, so the reported receipts remain the cost evidence.

In `legacy_text`, each treatment attempt keeps a `gptgrep.harbor.decisions-cost.v1` receipt in `decisions_cost` in every Decisions mode, derived from the product's reported `jev` accounting, including for a failed Ask. Rich multimodal attempts carry no such receipt, so their trial cost stays unknown. A trial's cost is known only when the product reports complete accounting, every attempted call returned a validated response and every response reports a finite cost; otherwise it stays null. The paired summary's `decisions` section aggregates the treatment receipts: `reported_cost_usd_total` is known only when all 62 trials are known, beside complete and unknown trial counts, the receipt count, a separately labelled known subtotal and `total_within_cap`. Reported costs keep `currency_verified=false` and are not added to query cost.

## Usage: Create Task Directories

The owner materializes `materialization.template.json` with three strict `{path,bytes,sha256}` pins: cohort projection, runtime contract and frozen primary judge contract. All paths must be physical absolute paths. Preserve the original frozen cohort pin in `source_cohort_sha256`.

The cohort projection schema is `gptgrep.harbor.cohort.v1`, with exactly `schema`, `source_cohort_sha256`, and `tasks`. It has exactly 62 distinct rows containing only `pair_id`, `document_id`, `question`, `reference`, and `answer_format`, covering exactly 34 document IDs. This projection is evaluator-owned private input. No source author opened or generated actual rows.

The judge contract schema is `gptgrep.harbor.primary-judge.v1`, with exactly `schema`, `prompt`, and `response_schema`. Root must derive it from the selected frozen primary judge, not write a new rubric. Its only formatting fields are `question`, `answer` (reference), `answer_format`, and `response` (complete candidate answer). The supported strict response schema has Boolean/string fields and requires Boolean `equivalent`. Because the Judge passes it as native strict structured output, every property must be listed in `required` exactly once and `additionalProperties` must be `false`; materialization rejects any other schema. Keep `required` in the frozen judge's property order: it fixes the order of `properties` in the Judge's schema file, and therefore the order in which the Judge generates its verdict keys. A different frozen schema requires a reviewed adapter change. No evidence annotations, raw documents, retrieval trace, other-arm output or extra evaluator rubric enter the primary prompt. Unsupported or oversized complete output is never silently truncated or called judged.

Fill `runtime.template.json` from selected owner evidence. Its `admission` is the existing pinned runtime review with `accepted=true`, `scope=harbor_full62_paired_once`, matching run ID, source cohort, profile, platform, image digests, binary, assets and judge hashes. It records `native_cli_contract_qualified`, `named_permissions_qualified`, `reader_effective_permissions_equal`, `bare_image_excludes_gptgrep_and_indexes`, and `raw_only_index_provenance_verified`, and joins the exact `native_cli` object. `runtime_subject_sha256` hashes compact sorted UTF-8 JSON over all runtime fields except `admission` and `admitted`. These fields bind the selected evidence; setting them does not manufacture acceptance.

Select `trial_order_seed` before results, separately from the analysis `bootstrap_seed`. The adapter uses independent deterministic streams to shuffle all 62 complete pair blocks and choose each pair's arm order, retaining adjacent paired trials and all 124 members. It freezes the explicit task-name sequence and digest in `export.trial_order`, then pins the complete Harbor job as `export.job`. The job uses `datasets=[]` and an ordered `tasks=[{path,source}, ...]` list, preserving the selected order through Harbor 0.24's existing task front door. Single-trial concurrency and zero retries remain explicit. The cohort and export task records retain their original order; runtime scheduling follows only the frozen list. `reader_base_binary` and `gptgrep_binary_pin` use strict in-container file pins. ## Notes & Caveats

Synthetic checks establish package and Harbor API behavior only. Selected-image qualification, the real 124 trials, independent results review and project delivery remain separate. No benchmark score, paid inference, finance acceptance or release acceptance follows from the synthetic suite.

The installed source and Harbor docs establish the integration interfaces. Actual native event shapes, CLI request metadata, account projection, generic tools and sandbox behavior still need the selected binary/image qualification before run. Requested fast, reported priority and actually served identity remain distinct. The INDEX helper may be independently built/admitted without replacing the SEARCH native reader.

Every outer query attempt and its observed wall duration is retained; there is no adapter retry. Partial failure output yields any parsable observed accounting. Unobserved model/provider retries and physical Decisions requests remain unknown. The final-reader token summary is a subset diagnostic and is never added to the model-turn ledger. Available reported retrieval cost is retained with its denomination unverified; missing native costs keep complete query cost and G5 normalization unavailable. INDEX and Judge costs remain separate. This adapter does not inspect unlisted financial ledgers.

Failure-aware time assigns the original deadline to wrong/failed tasks, bounds unavailable judgments, and never sums overlapping model durations as query wall time. Generic account/financial enforcement is supplied by the selected sandbox/owner admission, not implemented as a second money owner here. The process controller bounds each stream at 4 MiB, imposes the query deadline and permits at most two seconds for group cleanup. Escaped daemon/service custody is not proved by process-group cleanup; selected sandbox teardown remains required.

The materializer's `copy_asset` verifies finite supplied pins, not the semantic purity of a corpus or image. Independent source/image/index custody review establishes that no gold, task annotations or other-arm outputs are present. Complete source-only tests include malicious/missing binding cases but do not claim runtime sandbox isolation.

The adapter summary is a bounded SEARCH projection, not an implementation claim for every proposed INDEX metric in `metric-schema.json`. Grounding, citation entailment, served-profile proof, provider-internal counts, complete normalized costs, G5, independent acceptance, first-release PageIndex comparison, publication and Goal completion remain separate.

uv pip install --python "$UV_PROJECT_ENVIRONMENT/bin/python" --require-hashes \
