# Development storage

`environments-harness-self` owns the storage policy, executable checks, private
project registry, retention records and migration runbook. Its selected source
entry is `runbooks/22-storage-governance.md`; resolve the current owner through
the environment catalog. This project document is an entry to that contract,
not a second implementation or a machine-specific configuration.

Before any dependency installation, download, build, test, model/browser
acquisition or container operation, select the owner's verified executable or
source invocation and exact private policy. Use `environments-harness storage
--help` to check that the selected entry implements the required interface.
An older installed CLI, an unavailable policy or an unregistered worktree is a
stop condition. Do not replace the check with direct execution or guessed paths.

Each admitted active checkout keeps a small ignored `.local/development-storage.json`
locator for the owner's private policy and selected executable. The locator records
exact paths and review evidence; it is not a second registry and grants no admission
by itself. Keep machine details out of this portable document. An installed CLI's
availability does not prove that its interpreter or environment is externally placed.

Prepare an exact `storage plan` with the private policy and workload, project,
workspace, toolchain, unique run ID, output path and absolute command argv.
Review the plan's digest, physical volume identity, registered Git common-dir,
workspace identity, command, isolated paths and complete peak estimate. Execute
that plan through `storage run --plan ... --expect-digest ... --yes` with the same
argv. The command runner must produce a child startup receipt from the actual
child environment. A parent's exported variables, plan or successful process
does not prove worker inheritance or a tool's actual output location.

Each worker receives its own reviewed run and binding. A worker can use the
owner's `storage verify-env` to check that binding inside its actual command
runner. Recheck with `storage checkpoint` at phase boundaries and turn handoffs;
retain success, failure, cancellation and incomplete-run records. Outputs stay
isolated by project, repository, worktree, toolchain and run. Shared caches use
only explicitly registered package-manager concurrency. Tool-specific flags,
local project settings and temporary paths need actual-use validation; variable
names alone are not acceptance.

The private registry covers every known Git common-directory and classifies
each worktree. New worktrees, including checkouts of older commits, are denied
until admitted independently of their source revision. Historical or frozen
worktrees retain their original AGENTS and source bytes and remain read-only
nonconsumers. Registry coverage is distinct from runtime adoption. Arbitrary
direct shell commands are outside this cooperative launch gate; it does not
provide host-wide filesystem confinement.

The internal free-space floor is 100 GB and the target is 150 GB. Large workloads
stop below the floor. A small governance-validation exception must be explicitly
reviewed and bound to its command, timeout, paths, internal metadata ceiling and
download, unpack, output, cache, migration, rollback and safety-margin estimates.
It does not make the floor pass. Missing, wrong, read-only or insufficient
external storage must refuse before the child starts, without creating a
replacement mountpoint or falling back to internal storage.

Preserve source, uncommitted changes, Git relationships, checkpoints and
evaluation evidence. Migration requires writer/lock/reference checks, retained
copy, content/mode/link verification, reviewed binding switch and actual-use
proof. Original payload deletion, service interruption and global toolchain or
PATH changes retain their existing approval boundaries. Directory size and
container reclaimable estimates do not prove released filesystem space.

Keep exact paths, UUIDs, runtime identities, policies and receipts in the owner's
private state. Source checks, independent review, per-consumer adoption, tool
placement, container exceptions and actual net release are separate evidence.
These storage checks do not alter GPTgrep's research, live evaluation or release
gates.
